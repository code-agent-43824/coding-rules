# Правила для кодинг-агентов

Черновик свода. Собран из файлов правил в репозиториях `code-agent-43824`
(`CLAUDE.md`, `AGENTS.md`, `HANDOFF.md`, `CONTRIBUTING.md`, `.github/copilot-instructions.md`)
и из прямых указаний владельца.

В свод попали только те правила, которые **не противоречат друг другу** между
проектами. Спорные пункты вынесены в [OPEN-QUESTIONS.md](OPEN-QUESTIONS.md) и здесь
не зафиксированы — до решения владельца они не являются правилами.

У каждого пункта в скобках указано, из каких репозиториев он взят.

---

## 1. Git и коммиты

- **Коммитить напрямую в основную ветку. Ветки и pull request'ы не создавать.**
  Это прямое указание владельца, повторённое в пяти проектах.
  (powermath, coffee-taster, aurora-rutoken, partners-architector, home-assistant-settings)
- **Каждый завершённый логический шаг — отдельный коммит, сразу с `push`.**
  Не копить работу в один большой коммит.
  (aurora-rutoken, coffee-taster, partners-architector, 63fz-legal-tech)
- **Коммит должен быть самодостаточным и понятным без диффа** — сессию агента могут
  прервать в любой момент, следующий агент подхватывает по сообщению коммита и докам.
  (partners-architector, mobile-wallet-demo, kriptosfera)
- **Перед коммитом проверять `git diff --check` и `git status`.** Не втягивать чужие
  и сгенерированные файлы. (aurora-rutoken)
- **Перед началом работы — `git fetch` основной ветки** и учесть изменения других
  агентов. (aurora-rutoken)
- **Git — обычными прямыми командами.** GitHub API использовать только на чтение
  (статусы, логи, релизы, артефакты). (aurora-rutoken)

## 2. Порядок работы: документ → код → запись

Единый протокол, встречается в восьми проектах (различаются только имена файлов —
см. открытый вопрос 5).

1. **Сначала документ.** До изменения кода, CI, конфигурации или структуры — записать
   конкретное намерение в план/журнал проекта: что собираешься сделать и зачем.
   В `partners-architector` план **коммитится до того, как тронут код**.
2. **Потом работа.**
3. **Потом запись результата в том же изменении:** факт выполнения, следующий шаг,
   и приведение в порядок доков, которые разошлись с реальностью.

Цель: следующий агент понимает **что планировалось, что сделано и что дальше — из
одних доков**, не читая дифф. Если код и документация расходятся — чинить документацию
в том же изменении.
(aurora-rutoken, mobile-wallet-demo, kriptosfera, partners-architector, powermath,
63fz-legal-tech, coffee-taster, home-assistant-settings)

- **Что не записано — то не начато.** (partners-architector)
- **Документы-снимки состояния не обновляются сами.** Проверил или изменил реальный
  статус — сразу сверь и обнови соответствующий документ в этой же сессии, не
  оставляй устаревшие записи до отдельного запроса. (home-assistant-settings)
- **Неудачные попытки из журнала не удалять** — каждая закрывает гипотезу, к которой
  иначе вернёшься снова. (aurora-rutoken)

## 3. Проверка и честность отчёта

Самое устойчивое правило во всём наборе — формулировки разные, смысл один.

- **Не выдавать непроверенное за проверенное.** Если тесты не запускались (нет SDK
  в контейнере, нет устройства) — сказать это прямо, а не подразумевать, что всё
  прошло. (powermath)
- **Зелёный статус CI — не доказательство.** Для сборочных изменений смотреть
  фактические логи и артефакты. (aurora-rutoken)
- **Симуляция не превращается в утверждение о железе или безопасности.**
  (mobile-wallet-demo)
- **Пробелы закрываются данными, а не рассуждением.** Признаки, которых нет в
  подтверждённых фактах, в алгоритм не вносить: две правки «по догадке» уже дали
  неверный результат. (aurora-rutoken)
- **Не выдумывать содержимое предметной области** — текст закона, экспертные
  комментарии и т.п. (63fz-legal-tech)
- **Проверки соразмерны риску изменения.** (aurora-rutoken)

## 4. Зафиксированные решения не переоткрывать

В каждом проекте есть список решений, принятых осознанно и выглядящих как ошибка для
свежего взгляда. Их нельзя «чинить» по своей инициативе:

- `coffee-taster` — `keystore/debug.keystore` закоммичен намеренно (иначе обновление
  не встанет поверх установленного приложения и сотрёт данные владельца).
- `kriptosfera` — нулевые файлы-заглушки `payload.zip` / `cryptopro-plugin.zip` нужны
  для `go:embed`, удалять нельзя.
- `mobile-wallet-demo` — `dart_defines.json` закоммичен намеренно, это не утечка.
- `aurora-rutoken` — «вопрос закрыт»: не пытаться раззиповать артефакты Actions и не
  убирать релиз с голыми RPM.
- `home-assistant-settings` — звук дверного звонка не менять без явной просьбы;
  тему настроечных сущностей CO₂-датчика не поднимать повторно.

**Правило:** такие решения помечаются в правилах проекта явно, вместе с причиной.
Причина — обязательна: без неё следующий агент снесёт решение как мусор.
Отменяет их только владелец.

## 5. Секреты

- **Никогда не коммитить** учётные данные, токены, приватные ключи, персональные
  данные и продакшн-конфигурацию. (partners-architector, home-assistant-settings)
- Бинарники сторонних вендоров в git не класть — тянуть сборочными скриптами с
  фиксацией по SHA-256. (kriptosfera)
- **Осознанные исключения возможны, но только явные:** каждое фиксируется в правилах
  проекта с причиной, иначе следующий агент примет его за утечку и удалит
  (`dart_defines.json` в mobile-wallet-demo, webhook-URL в `.mcp.json` приватного
  home-assistant-settings).

## 6. Многоагентная работа

Часть репозиториев ведут несколько агентов одновременно.

- Изменения держать узкими и независимо проверяемыми — чтобы параллельный агент
  подхватил без конфликтов. (partners-architector, mobile-wallet-demo, kriptosfera,
  aurora-rutoken)
- Любая задача должна оставаться возобновляемой: сессию могут прервать в любой момент.
  (partners-architector)
- Роли могут быть разделены: в `partners-architector` деплоем занимается только агент
  Watson, остальные к проду не прикасаются.

## 7. Окружение

- **Окружение эфемерное** — настройку доступа к GitHub повторять в начале каждой
  сессии (`gh auth setup-git`, `git remote set-url origin …`).
  (home-assistant-settings)
- **Прокси среды отдаёт HTTP 403 на часть операций записи** — на `git push` тега и на
  запись через REST API. Это политика, а не сбой: не обходить, а сообщать.
  Тег версии в `aurora-rutoken` из-за этого ставит workflow, а не агент.
  (aurora-rutoken; подтверждено 2026-08-11 — удаление ветки через
  `git push --delete` и `gh api -X DELETE` тоже отдаёт 403)

## 8. Стиль решений

- Понятные скучные поддерживаемые решения предпочтительнее спекулятивных абстракций.
  (partners-architector)
- Зависимости, фреймворки и инфраструктуру добавлять только когда этого требует
  принятая спецификация и текущая фаза; всё сверх принятого стека — через
  зафиксированное решение (ADR). (partners-architector)
- Долгоживущие архитектурные решения записывать как ADR в `docs/decisions/`.
  (partners-architector)
